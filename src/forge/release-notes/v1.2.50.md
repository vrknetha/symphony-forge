# Forge v1.2.50

## What changes for client repos

- The coordinator now sees how full its chat is. When a Claude or Codex coordinator chat uses more than half of its context window, a hook adds one line with the token count and the window size. At the next quiet moment (after a merge or while checks run), the coordinator runs `forge hook handoff`, adds its open decisions, lessons and background-job log paths to `.git/forge/handoff.md`, and asks the owner to clear the chat. The guide's earlier rule "hand over at 20 to 30%, never past 40%" is replaced by "more than half, at a quiet moment".
- A new or cleared chat in a Forge repo starts with one line that names the handoff note and its date and says to read it first, then run `forge next`. Builder sessions do not get this line.
- When a repo's test setting runs one combined script and it has no quick-test setting, `forge doctor`, the upgrade and adoption say so in one line; Forge writes no setting. The guide tells the agent how to write, check and propose a quicker command through a small fix.
- On Windows, a builder's own test run skips each separate step of its test command that runs only Playwright or Cypress browser tests. The pull request check, the final check and the full test run still run them.
- When the latest full test run on the main branch fails, the board shows it under Needs you with a link to the run, and `forge next` marks it Needs you. It stays until a later full run passes.
- An Antigravity review that ends after a refused tool request no longer stops with "review engine returned empty output". It returns Neon's written review, or stops with a message that names the refused step.

- The explorer (idea sorting and code questions) runs on the family that `workers` picks, not on the coordinator chat's own family. Defaults: Codex `gpt-6.1-terra` at medium, Claude `claude-haiku-5-5`, Antigravity `gemini-4-neon` at low. A repo's own `[models.explore]` entries are kept.
- In a Codex chat the owner approves a story by typing the line `forge next` shows, `approve <KEY> <code>`; no Plan mode is needed. The code belongs to the shown "What changes for you" and "Done when"; a changed plan or a wrong code records nothing and says why. Only the owner's own message counts; messages in chats that Forge started (builders, reviews, `forge ask`) never approve. In Codex, trust the new hook once when the coordinator asks. Claude chats keep Plan Mode.
- Review findings show the reviewer's own severity next to whether they block the merge, so a finding no longer shows as P0 only because it blocks. The migration Harm floor applies only when the change adds or edits a migration.
- A Done-when item whose proof can exist only after the merge (for example main's full run) shows as "pending after merge" with its check and owner, in close's output and the pull request, and does not block the merge. A later review does not raise it again as new work.
- A Codex repair round that changes effort keeps the same conversation and sends the new effort with the turn, so the cached prompt is reused. A Codex builder conversation is shortened by Codex at about 120K tokens; each repair brief still lists the open findings and failing tests.
- After a story is approved, a background runner starts every part that nothing blocks, builds it with no chat open, checks it and merges it; fixes started with `forge start` go the same way. Forge starts the runner itself when Forge is used; it is not a system service and ends when nothing is left. It moves only work approved or started after it is installed, so older open items stay where they are. Builder, review and test commands never wake it. The coordinator no longer starts each part or watches each run; it answers notices and questions.
- When one item needs the owner (a builder question, a round limit, a stuck run, a size decision, a tool setup, a pull request a person must merge), only that item stops and the owner gets one desktop notice with the question or link; a summary notice comes when the work is done. An owner's stop survives a restart and is checked by every build and merge path.
- The coordinator guide says that a settings fix that edits forge.toml must name forge.toml in its Done-when, so the builder keeps the edit.

## Known issues

- **The half-window line can be missed on older Claude models.** A coordinator on an older Claude model with a 200K window (for example Opus 4.1) is measured against a 1M window, so it gets no line before the chat is shortened automatically. Workaround: use a current Claude model, or hand over by hand when the chat feels long.
