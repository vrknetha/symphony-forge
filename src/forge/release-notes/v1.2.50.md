# Forge v1.2.50

## What changes for client repos

- The coordinator now sees how full its chat is. When a Claude or Codex coordinator chat uses more than half of its context window, a hook adds one line with the token count and the window size. At the next quiet moment (after a merge or while checks run), the coordinator runs `forge hook handoff`, adds its open decisions, lessons and background-job log paths to `.git/forge/handoff.md`, and asks the owner to clear the chat. The guide's earlier rule "hand over at 20 to 30%, never past 40%" is replaced by "more than half, at a quiet moment".
- A new or cleared chat in a Forge repo starts with one line that names the handoff note and its date and says to read it first, then run `forge next`. Builder sessions do not get this line.
- When a repo's test setting runs one combined script and it has no quick-test setting, `forge doctor`, the upgrade and adoption say so in one line; Forge writes no setting. The guide tells the agent how to write, check and propose a quicker command through a small fix.
- On Windows, a builder's own test run skips each separate step of its test command that runs only Playwright or Cypress browser tests. The pull request check, the final check and the full test run still run them.
- When the latest full test run on the main branch fails, the board shows it under Needs you with a link to the run, and `forge next` marks it Needs you. It stays until a later full run passes.
- An Antigravity review that ends after a refused tool request no longer stops with "review engine returned empty output". It returns Neon's written review, or stops with a message that names the refused step.
- `forge start` sorts new ideas using the non-design builder family (`workers`, except that a repo with a single configured `tools` family uses that family unless `workers = "antigravity"`), not the coordinator chat's own family; when that family differs from the current chat, Forge runs that explorer directly and acts on its reply. Native in-chat `explorer` subagents (used for code questions inside a chat) still stay on each chat host's own family (`.codex/agents/explorer.toml` for Codex, `.claude/agents/explorer.md` for Claude). Built-in `explore` defaults are now Codex `gpt-6.1-terra` at medium effort, Claude `claude-haiku-5-5` at high effort, and Antigravity `gemini-4-neon` at low effort; new repos get these entries at setup, and upgraded repos use them for missing `[models.explore]` entries while keeping their own configured entries (run `forge sync` after changing them to refresh native explorer roles).
- In a Codex chat, the owner can approve a story without Plan Mode by typing `approve <KEY> <code>` (the 6-character code `forge next` shows for the current "What changes for you" and "Done when"). A changed plan or a wrong code records nothing and says why. Only the owner's own message counts; subagents and chats that Forge started (builders, reviews, `forge ask`) never approve. If the story still waits with no reason after typing the line, ask the owner to review and trust the new hook with `/hooks` in Codex. Codex Plan Mode and Claude Plan Mode still work as before.
- Review findings show the reviewer's own severity next to whether they block the merge in close's output and the pull request, so a finding no longer shows as P0 only because it blocks. The migration Harm floor applies only when the change adds or edits a migration across its commits; if an earlier review applied that floor without a migration change, close asks the reviewer to score that finding again.
- A Done-when item whose proof can exist only after the merge (for example, main's full test run) can use `check:` in the `Proof list:` and is recorded as an `After merge:` finding. It does not block the merge, stays listed under `Pending after merge:` with its check and owner across review rounds in close's output and the pull request, and is run by its owner after merge.
- A Codex repair round that changes effort keeps the same conversation and sends the new effort on the turn instead of on thread resume, so the cached prompt is reused while the run record keeps the effort used. For Codex builder turns, Forge sets auto-compaction at 120K total tokens so Codex shortens long builder conversations; each repair brief still lists the open findings and failing tests.
- After a story is approved or a fix is started (`forge start` or `forge fix start`), a background runner starts each unblocked part, builds and checks it through `forge land` with no chat open, and removes finished folders. The repo's merge setting decides how ready pull requests merge (`human` by default, while unsigned client prototypes merge by `agent` until sign-off, and migration, adoption and merge-switch fixes still merge by a human): when agent merges apply, the runner merges ready pull requests; when human merges apply, `forge land` stops once the pull request is ready and the runner polls GitHub (for up to 24 hours) until a person merges it, then tidies up and starts newly unblocked parts. Forge wakes the runner when Forge commands run (not from `forge test`, hooks other than approval and context, CI, or inside Forge builder, review or runner processes); it is not a system service and ends when nothing is left. It acts only on work approved or started after the runner is first installed on this machine, so older open items stay where they are. The coordinator no longer starts each part, starts each fix build, or watches background runs; it answers notices and builders' questions.
- When one item needs the owner (a builder question, a review round limit, a stuck run, a size decision, a tool setup, or a ready pull request a person must merge), only that item stops while other work keeps moving. On macOS and Linux, the owner gets one desktop notice per stopped state with the question or pull request link, and a summary notice when the runner finishes. On Windows, Forge sends no desktop notices, so Windows owners should check `forge next` or `forge board` for stopped items, questions and ready pull requests. An owner stop (`forge stop`) survives a runner restart and is checked by the runner, `forge merge`, and `forge work` / `forge close` / `forge land --all`; running `forge land <item>` directly lifts the stop.
- Workers edit `forge.toml` only when their fix's Done-when names `forge.toml` (never on a story part), and every settings-fix instruction in the coordinator guide now says the fix's `--done` must name `forge.toml` so a builder started by the runner keeps the edit instead of restoring the file.

## Known issues

- **The half-window line can be missed on older Claude models.** A coordinator on an older Claude model with a 200K window (for example Opus 4.1) is measured against a 1M window, so it gets no line before the chat is shortened automatically. Workaround: use a current Claude model, or hand over by hand when the chat feels long.
