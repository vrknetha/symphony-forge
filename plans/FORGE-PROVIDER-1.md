# A private repo's test jobs run on throwaway AWS machines

6 parts · Risks: the GitHub App key (repo Administration write) sits in your AWS account; the spend alarm is an email, not a stop; turning off cannot be undone · New moving parts: one AWS stack per repo (machine limit table, two small functions, a timer, a budget), one GitHub App

## What changes for you

In this plan, a "runner" is a machine that runs one GitHub Actions job. An "AWS runner" is a machine that starts in your AWS account for one job and is deleted when the job ends.

- AWS runners work for private repos only. For a public repo, Forge refuses to turn them on and says why in one line: GitHub says self-hosted runners should almost never be used for public repositories, because anyone can open a pull request against them. Forge's own public repo keeps GitHub's free runners; the first real use is a private trial repo. (Source: your decision of 27 Nov 2026)
- AWS runners are off by default. A new client repo gets them off at setup. An existing client repo has them off after it upgrades and syncs, and its settings and workflows do not change. Both get the new steps in Forge's guide. (Source: your decision of 27 Nov 2026)
- To turn them on, the agent asks you, then a first settings fix sets `aws_runners` in `forge.toml` to the AWS account and region, written `"<account number>/<region>"`, and a person runs setup. Only when setup says it is verified does a second settings fix set the existing `test_runner` setting to `"forge-aws"`. Until then the workflow keeps GitHub's runners, so no job waits for a runner that does not exist yet. That one AWS account pays for all of the repo's Actions jobs. A second clone of the repo sees the setup in AWS and makes nothing; a person who signs in to a different AWS account is refused and told which account pays. Laptop test runs and build rounds, in later stories, use the same account and the same machine limit. (Source: your decision of 27 Nov 2026; keeping the account and region in `forge.toml`, and the two-step turn-on with `test_runner`, are the planner's choices; confirm)
- With `test_runner` set to `"forge-aws"`, the repo's Linux test jobs (the pull-request test groups and the nightly full test run) run on AWS runners; Forge's existing `test_runner` setting already does this. The docs check, the review check and the final `tests` check stay on GitHub's machines. (Source: the planner's choice; confirm)
- Each job gets its own machine: 4 processors, 16 GiB of memory, Docker, and an official Ubuntu 24.04 image whose id Forge pins at setup. Docker is installed when the machine starts. A repo-specific image is made only if the install is measured slow, not in this story. GitHub's own runner for a private repo has 2 processors and 8 GB. The 16 GiB size is the one that later sandbox stories use too, so one size serves every story. (Source: your decision of 27 Nov 2026)
- At setup you choose how many machines may run at once, from 1 to 4. The default is 2. AWS enforces it, so it holds when your laptop is off. Extra jobs wait in GitHub's queue; GitHub ends a job that waits 24 hours. (Source: your decision of 27 Nov 2026)
- A machine stays alive only while it shows it is working. It marks every 5 minutes. AWS stops it after 15 minutes with no mark, or 3 hours after it started, whatever the marks say. The machine also switches itself off as a second layer. A place is free again only after AWS confirms that the machine is gone. (Source: your decision of 27 Nov 2026)
- At setup you choose a monthly amount and an email address. AWS emails you when the actual cost of the whole AWS account reaches that amount. There is no automatic stop. Setup prints the worst case: the machine limit times 3 hours. (Source: your decision of 27 Nov 2026; "whole account" is the planner's choice, because AWS cost tags take a day to start working)
- At setup you sign in to AWS with the AWS CLI version 2 on your laptop. Forge shows the account and region first. Then you create a GitHub App for the repo: Forge opens one small page on your own laptop that sends the App form to GitHub, you approve it on GitHub's page, and you install it on this one repo only. Forge refuses if the App can reach any other repo. The App has Administration write on that repo (GitHub needs this to make one-job runners) and Actions read. Its key and webhook secret go into AWS Secrets Manager. (Source: your decision of 27 Nov 2026; the one-repo check is the planner's choice; confirm)
- To turn AWS runners off, `forge lanes --aws off` deletes everything the setup made, checks that nothing is left, names anything that is left, and is safe to run again. Forge cannot delete the GitHub App; it names the page where you delete it. The guide also lists the plain AWS CLI steps, so cleanup works without Forge. (Source: your decision of 27 Nov 2026)
- Estimates, not measured. The machine type m7i.xlarge (4 processors, 16 GiB) costs about $0.19 an hour; with its public address and 30 GiB disk, about $0.198 an hour. Setup looks up the real price for your region. A 10-minute job plus 2 minutes of start time costs about $0.04. The two secrets cost about $0.80 a month. The timer, functions and table cost cents. With the limit at 2, 3 hours of both machines cost at most about $1.19; if every place stayed busy for a month, about $289. A machine takes about 2 to 5 minutes to become ready.
- Not known until the first real run: the real start time, how long the Docker install takes, if every generated test group fits in 16 GiB, if the pinned Ubuntu image runs the generated test groups without changes, and how soon GitHub removes a one-job runner that never got a job.
- The success measure, on the private trial repo: the median time from the start of an item to its ready pull request over one week before and one week after, with the AWS cost per item and the load-caused test failures beside it. `forge lanes --aws status` prints the AWS part for the last 7 days. (Source: your decision of 27 Nov 2026; the `status` readout is the planner's choice; confirm)
- Forge also deletes the old Mainline-only spec and replaces its three planned stories with the later stories in Notes. (Source: your decision of 27 Nov 2026)

Design: none (no product screen or page. Setup opens one local page on your laptop for a few minutes, only to pass the GitHub App form to GitHub; it has one button and no design. Setup, status and turn-off print lines in the agent's terminal.)

## Why

The laptop is the busiest part of the factory. Over 86 items from 11 to 14 Oct 2026, local tests and the wait for the test line took about 22% of item time. This story builds the AWS side that the later stories reuse: one place where AWS decides how many machines may run, and one lifetime rule. It tests that side first on the simplest job, the CI tests of a private repo. How much faster work gets ready is not measured yet.

## Done when

1. **With `aws_runners` and `test_runner` unset, which is the default in a new repo and in an existing repo after upgrade and sync, Forge makes no AWS or GitHub call and writes the same workflow as before; `forge lanes --aws setup` refuses, before it creates anything, a public repo, a laptop with no AWS CLI version 2 or no AWS sign-in, an AWS account or region other than the one in the setting, and a `test_runner` other than the AWS label, each with one line that says why; and with `test_runner` set to `forge-aws`, a generated workflow sends the Linux test jobs and the nightly full test run to the AWS label, and every other job stays on its old machine.**
2. **Setup in the right account makes the repo's AWS stack once, with the machine limit, the pinned image and the budget email, and prints the worst case; a second setup, also from a second clone, makes no second stack; a new limit changes the stack.**
3. **Setup refuses a GitHub App that can reach any repo besides this one, and says it is verified only when the stack, the App key and a one-repo install are in place; a job event from GitHub starts nothing unless its signature is right, its repo is this private repo and it asks for the AWS label; a repeated delivery counts once; the App's one-job runners come from GitHub's own call.**
4. **With the limit at 2, six queued jobs and a repeated delivery start at most two machines; a third starts only after AWS confirms that a machine is gone; a job that is cancelled while it waits starts none; each machine takes one job.**
5. **A machine without a mark for 15 minutes, or older than 3 hours even with marks, is stopped by AWS; the machine also switches itself off; a place is freed only after AWS confirms that the machine is gone.**
6. **`forge lanes --aws off` deletes the repo's AWS stack, machines, secrets and runner records, checks the result, names anything left, and a second run is safe.**

## Risks

These steps are sensitive or cannot be undone:

- The App key has Administration write on the repo. It can change the repo's settings, not only its runners. Anyone who can read the secret in your AWS account can use it. Forge never prints it. Setup refuses an install on more than this repo.
- Any workflow in the repo that asks for the AWS label runs on these machines, with internet access. Keep GitHub's setting "Run workflows from fork pull requests" off for the repo. Forge does not check it. A job from a repo that is not private starts nothing, so a repo that later turns public stops getting machines.
- The budget is an email. AWS updates cost about three times a day, so spend can pass the amount before the email comes. If every place stays busy all month the cost is about $289 at limit 2 (estimate).
- The 15-minute and 3-hour rules run once a minute and EC2 needs time to end a machine. A machine can live a few minutes longer than the rule says.
- Turn-off cannot be undone. It deletes the stack, its logs and the App key in AWS.

### Shared details

- **Settings.** `forge.toml` key `aws_runners`, a string, default `""` (off), else `"<12-digit account>/<region>"`, for example `"123456789012/ap-south-1"` (`KEYS` and `DEFAULTS` in `repo.py`; add it inside the existing lines). `aws.py` checks the shape. It names the sponsor; it does not move any job. Jobs move only when the existing `test_runner` is `"forge-aws"`, set in a second settings fix after setup says it is verified. The agent changes both only in a settings fix. Forge never edits `forge.toml`.
- **Names and tags.** The repo is known by its numeric GitHub id, `RepoId`, from `gh api repos/{owner}/{repo} --jq .id` run in the checkout, so a rename or an owner change breaks nothing. Stack `forge-runners-<RepoId>`. Every resource carries the tag `forge-runners=<stack name>`. Messages show the current `{owner}/{repo}`. Runner label `forge-aws`. No record is kept on the laptop for setup: the stack's parameters (`RepoId`, `MaxMachines`, `BudgetUsd`, `BudgetEmail`, `AmiId`) and outputs (`TableName`, `WebhookUrl`, `SecretArn`, `MachineRoleId`, function names) are the one home (`aws cloudformation describe-stacks`). Outputs hold no secret. `webhook` and `tick` take the repo's current full name from `GET /repositories/{RepoId}` (a webhook payload also names it) and check `repository.id` against `RepoId`, never the name.
- **One stack per repo** (the planner's choice; Astra split a shared base from per-repo bindings, which one repo does not need): VPC with one public subnet and an internet gateway (no NAT, no inbound security-group rule); launch template (below); DynamoDB table (on demand, key `pk` string, TTL attribute `ttl`); two Node.js 22 Lambda functions, `webhook` (function URL, auth type `NONE`, plus the permissions that AWS's function URL page requires for that auth type on the day of the build) and `tick`; an EventBridge Scheduler schedule `rate(1 minute)` for `tick`, flexible window off; one Secrets Manager secret `{"app_id", "pem", "webhook_secret"}` (an empty shell until INTAKE fills it); explicit log groups (so deletion removes them); an AWS Budgets monthly actual-cost budget (notification only, whole account); the IAM roles. FOUNDATION writes every role in full so later parts add code only. Webhook role: DynamoDB `GetItem`, `PutItem`, `UpdateItem`, `DeleteItem`, `Query`, `TransactWriteItems` on the table; `ec2:RunInstances` on each resource type that the call touches: `instance/*`, `volume/*` and `network-interface/*` in the region, the one image `image/<AmiId>`, and this stack's launch template, subnet and security group (a condition limits `ec2:InstanceType` to `m7i.xlarge`); `ec2:CreateTags` on instance, volume and network-interface with `ec2:CreateAction` equal to `RunInstances`; `iam:PassRole` for the machine role only; read of the secret. Tick role: the same, plus `ec2:TerminateInstances` on instances whose tag `forge-runners` is this stack, and `ec2:DescribeInstances` on `*` (it has no resource-level permission). Machine role (instance profile): `dynamodb:GetItem` and `dynamodb:UpdateItem` on the table, with the condition `ForAllValues:StringEquals` on `dynamodb:LeadingKeys` equal to `${aws:userid}`; for an instance role that value is `<role id>:<instance id>`, so a machine reaches only its own machine item (below) and nothing else.
- **Machine (launch template).** `m7i.xlarge`, On-Demand, x86-64, 30 GiB encrypted gp3 root disk deleted on termination, no key pair, public IPv4, IMDSv2 required with hop limit 1 (containers in a job cannot reach the machine's role), `InstanceInitiatedShutdownBehavior=terminate`. Image: setup reads the public parameter `/aws/service/canonical/ubuntu/server/24.04/stable/current/amd64/hvm/ebs-gp3/ami-id` in the chosen region (Canonical's documented naming scheme; the builder checks it with `aws ssm get-parameter`), checks with `aws ec2 describe-images` that the owner is Canonical (`099720109477`), and stores the id as the stack parameter `AmiId`. A later setup keeps the stored id.
- **Slot table.** A slot is a machine, not a run. Items: `slot#<1..MaxMachines>` (a held place: `kind` `actions`, `work` a list of what runs on the machine, `state` of `launching`, `running` or `terminating`, `instance`, `runner_id`, `launched_at`, and `jit` only until the launch call has returned), `<MachineRoleId>:<instance id>` (the machine's own item, key spelled exactly as `${aws:userid}` gives it: `slot`, `launched_at`, `jit` until used, `mark`, `ttl` 4 hours), `work#<id>` (stops one piece of work from taking two places; for Actions the id is the GitHub job id), `wait#<id>` (work that waits: `kind`, `repo`, `labels`, `queued_at`, `branch`), `done#<id>` (`kind`, `branch`, `minutes`, `ttl` 14 days). Story 1 writes one entry in `work` and starts one machine for it, because a one-job runner takes one job. The lifetime rule, the mark, the limit and the confirmed-termination rule belong to the machine, never to its job, so the later stories can put several build rounds and test runs on one machine (see Notes); keep `kind` and the list of work, and add no one-run-per-machine assumption to `admit.mjs`, `tick.mjs` or `reap.mjs`. A claim is one `TransactWriteItems` of two puts, `work#<id>` and the first free `slot#<i>`, each with `attribute_not_exists(pk)`. A release deletes the slot, the `work#` item and the machine item. A slot above a lowered limit is never claimed again.
- **Lifetime numbers.** `reap.mjs`: marks every 300 s, stale at 900 s without a mark (the machine item starts with `mark` equal to `launched_at`, so a machine that never boots is stopped at 15 minutes), hard maximum 10,800 s from `launched_at`.
- **Hourly price for messages.** Setup asks `aws pricing get-products` (Price List API; its endpoint is in `us-east-1`) for `m7i.xlarge`, the chosen region code, Linux, shared tenancy, no software, used capacity, on-demand, and adds `$0.008` an hour for the public address and the disk. If the call fails, setup prints `Price lookup failed; the worst-case numbers use $0.198 an hour, the estimate above.` and goes on.

4. ADMIT. Slots, launch and waiting jobs.
