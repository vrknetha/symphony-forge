# Builder test runs go to a throwaway AWS box when the laptop is busy

7 parts · Risks: unsaved work and approved test files leave the laptop for your own AWS account; an existing AWS setup must be updated once; a box that ends mid-run loses that run's time · New moving parts: one private storage bucket, one second machine role, one test-files secret and one start script, all inside story 1's AWS stack; one setup option; two settings

## What changes for you

In this plan, a "box" is a throwaway AWS machine that runs your tests for you. A "test run" is the tests that a builder runs with `forge test` or `forge test --change`, and the test step of `forge close`. The "laptop line" is the queue that holds test runs on your laptop today.

- Box test runs are off by default. A new client repo gets them off at setup. An existing client repo has them off after it upgrades and syncs, and its settings and workflows do not change. Both get the new steps in Forge's guide. A repo that already runs story 1's AWS setup must run `forge lanes --aws setup` once more to add the box parts to its stack; until it does, a run says so in one line and stays on the laptop. (Source: your decision of 27 Nov 2026)
- Boxes work for public repos and private repos. To turn them on, the agent asks you, then a settings fix sets `aws_tests = true` in `forge.toml`. The repo also needs `aws_runners` (story 1's setting for the AWS account and region, written `"<account number>/<region>"`) and a stack. The option `forge lanes --aws setup --tests-only` makes that stack with no GitHub App, no public web address and no public-repo check. Story 1's plain `setup` still refuses a public repo, and its refusal names `--tests-only`. Forge reads `aws_runners`, `aws_tests` and `aws_test_files` only from the default branch's `forge.toml`, never from the branch being tested. The same AWS account pays, and the same machine limit (1 to 4, default 2) covers Actions jobs and boxes together. (Source: your decision of 28 Nov 2026; the default-branch rule is the planner's choice; confirm)
- With `aws_tests` on, a test run starts on the laptop while the load is under 0.75 per core (half of today's limit of 1.5) and the laptop is not swapping memory to disk. If either fails, the run goes to a box at once and prints one line that says which. With `aws_tests` off, nothing changes: no AWS call, and the run waits in the laptop line as today. A reading Forge cannot take, every Windows laptop, and every run on GitHub Actions keep the run where it is. A run that is already inside a box never starts another box. "Swapping" means that the count of memory pages written to disk grew during one second (Linux `/proc/vmstat` `pswpout`; macOS `vm_stat` `Swapouts`), the same rule on both. It does not mean "a swap file exists": on the laptop where this plan was written, 16,276 MB of 17,408 MB of swap is used at this moment, so that reading would send nearly every run to a box. (Source: your decisions of 27 and 28 Nov 2026)
- Only these runs can go to a box, and each one asks for it by name: `forge test`, `forge test --change` and the test step of `forge close`. The full suite, the retest before a merge, the replay of an older revision and the pytest picker stay on the laptop. (Source: your decision of 28 Nov 2026)
- What goes to the box: your files as they are now (committed, unsaved and new files that git does not ignore) and the old version of each changed file (from the merge base with the default branch, which the repo already holds), so the box can see what changed. No other git history, and never a file that git ignores. A repo with submodules stays on the laptop. Forge first checks that the checkout is this repo's own GitHub repo and not a fork. The files go through a private bucket in your AWS account, and the bucket deletes them after 1 day. (Source: your decision of 28 Nov 2026; the fork check and "no history" are the planner's choice; confirm)
- Ignored test files (for example a local settings file) can go too, one file at a time. The agent lists the ignored files a run may need, you say yes or no to each name, and each yes is a settings fix that adds the name to `aws_test_files` in `forge.toml`. `forge lanes --aws files` then copies exactly those files into one AWS Secrets Manager secret (at most 64 KB after encoding). Each box run reads the secret, writes the files into the run's own folder, and deletes them when the run ends. (Source: your decision of 27 Nov 2026)
- A box has 4 processors, 16 GiB of memory and Docker, and is the same kind of machine as story 1's. Forge runs inside it, at the version `forge.toml` pins. A box holds no GitHub, Claude or Codex sign-in; it can read only the approved test files. It holds at most two runs, each limited to 2 processors, each as its own user on the box, and its own test line checks memory before each starts. It takes new runs only in its first 2 hours, aims to end by 3 hours (story 1's marks and limit), and AWS ends it after 10 minutes with no run on it. A new box is ready after about 2 to 5 minutes plus the install time. (Source: your decisions of 27 and 28 Nov 2026)
- When no box place is free (the limit is reached, or all boxes hold two runs), the run does not wait in AWS. It goes to the laptop line and says so in one line. (Source: your decision of 28 Nov 2026)
- A box run gives the same result as a laptop run: the exit code, the names of failed tests, the one retry of failed files where a laptop run retries, and the log. A failing test is a result. It never sends the run back to the laptop. When AWS or the box fails before the tests ran, and Forge has confirmed that the box's command ended or the box is gone, the run goes to the laptop line with one line of reason, and only that run's time is lost. When Forge cannot confirm it, the run fails with one line and the box keeps its place until it ends, so a test never runs twice at once. (Source: your decision of 27 Nov 2026; the confirm rule is the planner's choice; confirm)
- A box run shows in `forge lanes` and in the Forge pane as an ordinary test row marked "in a box", with its minutes. It takes no place in the laptop's test line. `forge stop <item>` cancels the command in the box and frees its place once the end is confirmed; it waits at most 2 minutes, and if nothing is confirmed the place stays held until the box ends. (Source: your decision of 27 Nov 2026)
- To turn boxes off, a settings fix sets `aws_tests = false`, clears `aws_test_files` and, when story 1's AWS runners are on, removes `test_runner = "forge-aws"`, and merges (`off` refuses while the default branch still has that `test_runner`); then `forge lanes --aws off --region <region>` runs in the same AWS account and region; then a settings fix sets `aws_runners = ""`. `off` also deletes the bucket (and its unfinished uploads) and the test-files secret, and checks that nothing is left. `forge lanes --aws status` also counts test runs and box minutes for the last 7 days, per branch, with unused box time. (Source: your decision of 27 Nov 2026; the `status` lines are the planner's choice)
- Estimates, not measured. A box costs about $0.198 an hour (story 1's number). A 10-minute test run in a box that is already ready costs about $0.03. A new box adds 2 to 5 minutes of start time. The test-files secret costs about $0.40 a month; the bucket costs cents. With the limit at 2, the estimate for one 3-hour batch is the same as story 1's: about $1.19. Boxes add no new limit, because they share story 1's. Replacements, storage, traffic and function calls can add charges; the budget is an email.
- Not known until the first real run: how long a box takes to become ready, how long the Forge install takes, if a fresh box has what a repo's own test command needs (language tools and packages), how big an upload gets for a large repo, and how often the laptop is busy.
- The success measure is story 1's: the median time from the start of an item to its ready pull request over one week before and one week after, with the AWS cost per item and the load-caused test failures beside it. (Source: your decision of 27 Nov 2026)

Design: none (no new screen or page. The pane gets one label, "in a box", on rows it already shows. Setup, status and turn-off print lines in the agent's terminal.)

## Why

The laptop is the busiest part of the factory. Over 86 items from 11 to 14 Oct 2026, local tests and the wait for the test line took about 22% of item time, and a heavy laptop also makes tests fail for load, not for a bug. Story 1 builds the AWS side: one place where AWS decides how many machines may run, and one lifetime rule. This story uses it for the next simplest work: the test runs that already wait on the laptop. It keeps the laptop first, so a quiet laptop costs nothing. How much faster work gets ready is not measured yet.

## Done when

1. **With `aws_tests` unset, which is the default in a new repo and in an existing repo after upgrade and sync, a test run makes no AWS call and waits in the laptop line as before; with it set (on the default branch), only `forge test`, `forge test --change` and the test step of `forge close` can go to a box, and a run stays on the laptop while the load per core is under 0.75 and the laptop is not swapping (swap-out count growing over one second), and goes to a box at once, with one line that says why, when either fails; a reading Forge cannot take, a Windows laptop, a GitHub Actions run and a run inside a box stay where they are.**
2. **A box run tests an upload of the allowed working tree plus the old version of each changed file, with no git history beyond those old versions, no ignored file and no submodule, sent through the repo's private bucket only after Forge checks that the checkout is this repo's own GitHub repo; only the names in `aws_test_files` come from Secrets Manager, and `forge lanes --aws files` refuses any other path and any payload over 65,536 bytes after encoding; and the run's folder, those files and the upload on the box are deleted when the run ends, whether the tests passed, failed or were stopped.**
3. **`forge lanes --aws setup --tests-only` makes the stack with no GitHub App, no public web address and no public-repo check, and plain `setup` on a public repo refuses and names it; a stack from before this story is found from its outputs on the laptop and the run stays on the laptop with one line; and the box role cannot read the GitHub App secret or any Parameter Store value, nor can the Actions machine role read the test-files secret or the bucket.**
4. **With the limit at 2, five test runs at once start at most two boxes with two runs each (a box that is still starting takes reservations up to its size), the fifth is told no place is free, and a box counts against the same limit as an Actions job; a run joins a box only in its first 2 hours; a box is ready only when Docker, the pinned Forge, the Session Manager agent and the language tools work; a box ends by 3 hours, and AWS ends it after 10 minutes with no reserved or running work.**
5. **A run in a box returns the exit code, the names of failed tests, the retry of failed files where a laptop run retries, and the log, in the form a laptop run gives, and a failing test never sends the run back to the laptop; when a call fails, no place is free, the box is not ready in 10 minutes or the box ends before the tests ran, and Forge has confirmed that the box's command ended or the box is gone, the run goes to the laptop line with one line of reason, runs there once, and leaves no place held; when Forge cannot confirm it, the run fails and says so, and nothing runs twice.**
6. **A box run shows in `forge lanes` (text and JSON) and in the pane as a test row marked "in a box" with minutes and takes no laptop test place; `forge stop <item>` cancels it, confirms the end, and frees its place only then; `forge lanes --aws off` leaves no bucket, no unfinished upload and no test-files secret, and `status` counts test runs and unused box time.**

## Risks

These steps are sensitive or cannot be undone:

- Two runs on one box are separate users, but a test that uses Docker can still reach the other run, as Docker access is root access. Both runs are from people of one repo; nobody outside it can reach a box.
- Your unsaved work leaves the laptop. It goes to a private bucket in your own AWS account, not to anyone else, and it is deleted after 1 day. A file that git does not ignore goes in even if it holds a secret, so keep secrets in ignored files. The old version of a changed file goes too; it comes from the merge base, which the default branch already holds. In a public repo, this is still your own account; nothing goes to the public repo.
- The approved test files may hold credentials. They sit in Secrets Manager and are read by the box that runs your tests, and the repo's test code runs there with internet access. Approve only values made for tests, never production keys. Deleting the AWS copy revokes nothing, so change such a value at its source. The box holds no other sign-in and cannot read story 1's GitHub App key.
- An existing AWS setup is changed once, when the person runs `forge lanes --aws setup` again: a second machine role, a bucket and a secret are added to the stack. Nothing runs until `aws_tests` is set.
- A tests-only setup has no public web address at all. Boxes start only from calls that your signed-in AWS account makes.
- A box that ends while a run goes (no marks for 15 minutes, 3 hours, or the idle end) loses that run's time. The run starts again on the laptop only when Forge has confirmed the first run ended.
- A fresh box may lack what a repo's own test command needs. Then the test fails in the box for that reason and looks like a real failure. The first real runs measure this.
- Boxes can raise spend, up to story 1's estimate. The budget is still an email, not a stop.
- A wrong swap or load reading costs money (an extra box) or time (a slow laptop), never a wrong test result.
