# Builder test runs go to a throwaway AWS box when the laptop is busy

6 parts · Risks: unsaved work and approved test files leave the laptop for your own AWS account; an existing AWS setup must be updated once; a box that ends mid-run loses that run's time · New moving parts: one private storage bucket, one second machine role, one test-files secret and one start script, all inside story 1's AWS stack; one setting pair

## What changes for you

In this plan, a "box" is a throwaway AWS machine that runs your tests for you. A "test run" is the tests that a builder runs with `forge test` or `forge test --change`, and the test step of `forge close`. The "laptop line" is the queue that holds test runs on your laptop today.

- Box test runs are off by default. A new client repo gets them off at setup. An existing client repo has them off after it upgrades and syncs, and its settings and workflows do not change. Both get the new steps in Forge's guide. A repo that already runs story 1's AWS setup must run `forge lanes --aws setup` once more to add the box parts to its stack; until it does, a run says so in one line and stays on the laptop. (Source: your decision of 27 Nov 2026)
- To turn them on, the agent asks you, then a settings fix sets `aws_tests = true` in `forge.toml`. It needs `aws_runners` (story 1's account and region) and story 1's setup. The same AWS account pays, and the same machine limit (1 to 4, default 2) covers Actions jobs and boxes together. Story 1's rule stays: private repos only, so Forge's own public repo cannot use boxes. (Source: your decision of 27 Nov 2026; the second setting and the private-repo limit are the planner's choices; confirm)
- With `aws_tests` on, a test run starts on the laptop while the load is under 0.75 per core (half of today's limit of 1.5) and the laptop is not swapping memory to disk. If either fails, the run goes to a box at once and prints one line that says which. With `aws_tests` off, nothing changes: no AWS call, and the run waits in the laptop line as today. A reading Forge cannot take, and every Windows laptop, keeps the run on the laptop. A run that is already inside a box never starts another box. "Swapping" means the count of memory pages written to disk grew during one second (Linux `/proc/vmstat` `pswpout`; macOS `vm_stat` `Swapouts`). It does not mean "any swap file exists": on the laptop where this plan was written, 16,276 MB of 17,408 MB of swap is used at this moment and the load is 6.6 on 8 cores, so the plain reading would send nearly every run to a box. (Source: your decision of 27 Nov 2026; the swap definition is the planner's choice; confirm)
- Only these runs can go to a box: `forge test`, `forge test --change` and the test step of `forge close`. The full suite, the retest before a merge, the replay of an older revision and the pytest picker stay on the laptop. (Source: the planner's choice; confirm)
- What goes to the box: one git bundle of your work, made from your commits plus a snapshot of tracked and untracked files that git does not ignore, so the box tests what the laptop run would test. Ignored files never go in by this path. The bundle goes through a private bucket in your AWS account, and the bucket deletes its files after 1 day. (Source: your decision of 27 Nov 2026 says "only committed code"; the snapshot of unsaved work is the planner's choice, because a builder tests unsaved work all through a round; confirm)
- Ignored test files (for example a local settings file) can go too, one file at a time. The agent lists the ignored files a run may need, you say yes or no to each name, and each yes is a settings fix that adds the name to `aws_test_files` in `forge.toml`. `forge lanes --aws files` then copies exactly those files into one AWS Secrets Manager secret (at most 64 KB in all). Each box run reads the secret, writes the files into the run's own folder, and deletes them when the run ends. (Source: your decision of 27 Nov 2026)
- A box has 4 processors, 16 GiB of memory and Docker, and is the same kind of machine as story 1's. Forge runs inside it, at the version `forge.toml` pins. It holds at most two runs at once, and its own test line decides when each starts, by its processors and memory, with the laptop's lane rules. A box takes new runs only in its first 2 hours and ends by 3 hours (story 1's marks and 3-hour limit), and it also ends when it has run nothing for 10 minutes. A box that was just started is ready after about 2 to 5 minutes plus the install time. (Source: your decision of 27 Nov 2026; the 10-minute idle end is the planner's choice; confirm)
- When no box place is free (the limit is reached, or all boxes hold two runs), the run does not wait in AWS. It goes to the laptop line and says so in one line. (Source: the planner's choice; confirm)
- A box run gives the same result as a laptop run: the exit code, the names of failed tests, the one retry of failed files and the log. A failing test is a result. It never sends the run back to the laptop. When AWS or the box fails before the tests ran (a call fails, the box is not ready in 10 minutes, or the box ends while the run goes), the run goes to the laptop line with one line of reason, and only that run's time is lost. (Source: your decision of 27 Nov 2026)
- A box run shows in `forge lanes` and in the Forge pane as an ordinary test row marked "in a box", with its minutes. It takes no place in the laptop's test line. `forge stop <item>` ends it: the command is cancelled in the box and its place is freed. (Source: your decision of 27 Nov 2026)
- `forge lanes --aws off` (story 1) also deletes the bucket and the test-files secret, and checks that nothing is left. `forge lanes --aws status` also counts test runs and box minutes for the last 7 days, per branch. (Source: your decision of 27 Nov 2026; the `status` lines are the planner's choice)
- Estimates, not measured. A box costs about $0.198 an hour (story 1's number). A 10-minute test run in a box that is already ready costs about $0.03. A new box adds 2 to 5 minutes of start time. The test-files secret costs about $0.40 a month; the bucket costs cents. With the limit at 2, the worst case for 3 hours is the same as story 1's: about $1.19. Boxes add no new worst case, because they share its limit.
- Not known until the first real run: how long a box takes to become ready, how long the Forge install takes, if a fresh box has what a repo's own test command needs (language tools and packages), how big a bundle gets for a large repo, and how often the laptop is busy.
- The success measure is story 1's, on the private trial repo: the median time from the start of an item to its ready pull request over one week before and one week after, with the AWS cost per item and the load-caused test failures beside it. (Source: your decision of 27 Nov 2026)

Design: none (no new screen or page. The pane gets one label, "in a box", on rows it already shows. Setup, status and turn-off print lines in the agent's terminal.)

## Why

The laptop is the busiest part of the factory. Over 86 items from 11 to 14 Oct 2026, local tests and the wait for the test line took about 22% of item time, and a heavy laptop also makes tests fail for load, not for a bug. Story 1 builds the AWS side: one place where AWS decides how many machines may run, and one lifetime rule. This story uses it for the next simplest work: the test runs that already wait on the laptop. It keeps the laptop first, so a quiet laptop costs nothing. How much faster work gets ready is not measured yet.

## Done when

1. **With `aws_tests` unset, which is the default in a new repo and in an existing repo after upgrade and sync, a test run makes no AWS call and waits in the laptop line as before; with `aws_tests` set, a run stays on the laptop while the load per core is under 0.75 and the laptop is not swapping, and goes to a box at once, with one line that says why, when either fails; a reading Forge cannot take keeps the run on the laptop, and a run inside a box never starts another box.**
2. **A box run tests a bundle of the committed code plus a snapshot of unsaved, not ignored files, sent through the repo's private bucket; only the names in `aws_test_files` come from Secrets Manager, and `forge lanes --aws files` refuses any other path; and the run's folder, those files and the bundle on the box are deleted when the run ends, whether the tests passed, failed or were stopped.**
3. **With the limit at 2, five test runs at once start at most two boxes with two runs each, the fifth is told no place is free, and a box counts against the same limit as an Actions job; a run joins a box only in its first 2 hours; a box is ready only when Docker, the pinned Forge and the AWS CLI work; a box ends by 3 hours, and after 10 minutes with no run; and the box role cannot read the GitHub App secret, nor can the Actions machine role read the test-files secret.**
4. **A run in a box returns the exit code, the names of failed tests, the one retry of failed files with its "Flaky test files" line, and the log, in the form a laptop run gives; a failing test is returned as a result and never sends the run back to the laptop.**
5. **When a call fails, no place is free, the box is not ready in 10 minutes, or the box ends while the run goes, the run goes to the laptop line with one line of reason, runs there once, and leaves no place held in AWS.**
6. **A box run shows in `forge lanes` (text and JSON) and in the pane as a test row marked "in a box" with minutes and takes no laptop test place; `forge stop <item>` cancels it and frees its place; `forge lanes --aws off` leaves no bucket and no test-files secret, and `status` counts test runs.**

## Risks

These steps are sensitive or cannot be undone:

- Your unsaved work leaves the laptop. It goes to a private bucket in your own AWS account, not to anyone else, and it is deleted after 1 day. A file that git does not ignore goes in even if it holds a secret, so keep secrets in ignored files.
- The approved test files may hold credentials. They sit in Secrets Manager and are read by the box that runs your tests, and the repo's test code runs there with internet access. Approve only values made for tests, never production keys. The box has its own role: it cannot read story 1's GitHub App key, and Actions machines cannot read the test files.
- An existing AWS setup is changed once, when the person runs `forge lanes --aws setup` again: a second machine role, a bucket and a secret are added to the stack. Nothing runs until `aws_tests` is set.
- A box that ends while a run goes (no marks for 15 minutes, 3 hours, or the idle end) loses that run's time. The run starts again on the laptop.
- A fresh box may lack what a repo's own test command needs. Then the test fails in the box for that reason and looks like a real failure. The first real runs measure this.
- Boxes can raise spend, up to story 1's worst case. The budget is still an email, not a stop.
- A wrong swap or load reading costs money (an extra box) or time (a slow laptop), never a wrong test result.

### Shared details

- **Settings.** `aws_tests`, a bool, default `false`; `aws_test_files`, a list of repo-relative paths, default `[]` (`KEYS` and `DEFAULTS` in `repo.py`, inside the existing lines). Forge never edits `forge.toml`; the agent changes both only in a settings fix. `aws_tests = true` with `aws_runners` unset prints the line under Messages and keeps the run on the laptop.
- **Routing signals** (`src/forge/box_route.py`). `busy()` returns a reason or `None`: load per core from `machine._load_per_core()` at or above `machine.LOAD_LIMIT / 2` gives `load {x} per core`; `swapping()` reads the page counter twice, 1 second apart (Linux: `pswpout` in `/proc/vmstat`; macOS: the `Swapouts:` line of `vm_stat`) and gives `it is writing memory to disk` when the count grew. An unreadable source, a missing `getloadavg` (Windows) and `FORGE_IN_BOX=1` give `None`. The low-memory wait of `machine._wait` stays as it is and is not a reason to use a box. Forge's own full test line is not a reason either (the owner named two signals).
- **Where the choice sits.** In `review.test_run`, after the skip and dirty checks and before `machine.join("test", ...)`. A run is a candidate only when `command == review.close_test(top, base, closing=closing)` (the recipe the box can repeat with `forge test` or `forge test --change`), which leaves the merge retest, the full suite and the replay on the laptop. The hook is `box_run.run(top, recipe)` returning `(status, report)`, or `None` for "stay on the laptop", which continues into the existing code unchanged. A fallback is `None` plus one printed line. The recipe is `{"closing": bool, "always": bool, "base": "<ref>"}`; the box runs `forge test` (plus `--change` when closing) with `FORGE_BOX_RECIPE` carrying `always` and `base`, which `fasttest.test` reads (at most 4 lines there). The builder checks that `close.py`'s `review_ref` is what `forge test --change` uses as `base`; if not, `base` travels in the recipe.
- **A box row.** The run's lane entry (`machine.join` still makes it, so `forge stop`, the pane and the timing records see it) is marked `box = {"provider": "aws", "work": "<uuid>", "instance": "<id>", "command": "<ssm id>", "since": "<iso>"}`, `admitted = true` and `processes = 0`, so it holds no laptop place and `test_allocation` ignores it. `lanes()` adds `box_minutes` and prints `({kind}, in a box, {n} min)`.
- **AWS side** (`webhook.mjs` direct-invoke branch, beside story 1's `{"check": "install"}`; `admit.mjs`). Three verbs through `aws lambda invoke --function-name <webhook> --payload ...`: `{"box": "claim", "work": id, "branch": b, "pin": "<forge version>"}`, `{"box": "status", "work": id}`, `{"box": "release", "work": id, "branch": b, "minutes": n}`. `claim`: (1) pick a running slot with `kind` `test`, `launched_at` less than 7,200 s ago, `ready`, and fewer than 2 entries in `work` (the one with the most entries first, so boxes fill before a new one starts): one `TransactWriteItems` puts `work#<id>` (`attribute_not_exists`) and appends to the slot's `work` with those conditions; (2) else claim the first free `slot#<i>` exactly as story 1 does, launch with `kind` `test` from the test launch template, `ClientToken` `test-<id>`, and user data `guest_tests.sh` (table, region, slot, bucket, secret ARN, pin; no secret); (3) else answer `{"state": "none", "reason": "no place free"}`. The constant `2` runs per box is 4 processors divided by the 2 processors a builder's run uses; the box's own test line enforces memory. `status` answers `state`, `ready`, `instance`. `release` removes the work from the slot, deletes `work#<id>`, and writes `done#<id>` (`kind` `test`, `branch`, `minutes`, `ttl` 14 days). `tick` writes `done#<instance>` with the machine's minutes when it frees a test slot. A `claim` on a stack from before this story (no bucket output) answers `{"state": "old"}`.
- **Stack changes** (`stack.yml`, applied by the next `forge lanes --aws setup`, which story 1 already runs as an update when the template changes). A bucket `forge-tests-<RepoId>-<account>-<region>` (private, all public access blocked, encrypted, lifecycle expiry 1 day, tagged `forge-runners=<stack>`); a secret `forge-tests-files-<RepoId>` (empty shell `{}`); a second role and instance profile `TestMachineRole` with `AmazonSSMManagedInstanceCore`, `s3:GetObject` on `runs/*/in/*`, `s3:PutObject` on `runs/*/out/*`, `secretsmanager:GetSecretValue` on the test-files secret only, and story 1's `dynamodb:LeadingKeys` condition for its own machine item (key `<TestMachineRoleId>:<instance id>`); a second launch template that differs from story 1's only by that profile; the webhook role gains `iam:PassRole` for `TestMachineRole` and `ec2:RunInstances` on the new launch template; story 1's machine role gets nothing new, and `TestMachineRole` has no right to the App secret. New stack outputs: `BucketName`, `TestSecretArn`, `TestMachineRoleId`. Setup's zip also carries `guest_tests.sh` and `run_box.sh`.
- **Run flow** (`src/forge/box_run.py`, laptop side). (1) `sts` account and region equal `aws_runners`; (2) `claim`: `none` or `old` is a fallback; (3) build the snapshot and upload it (SHIP); (4) poll `status` every 5 s until `ready`, at most 10 minutes (then release and fall back); (5) `aws ssm send-command --document-name AWS-RunShellScript` with one short line that fetches `runs/<id>/in/run_box.sh` from the bucket and runs it (the 4,096-character command limit); (6) poll `aws ssm get-command-invocation` every 5 s; (7) read `runs/<id>/out/result.json`, `log` and `results`, write the log to the entry's `output_path` and the results to `review.results_path(top)`; (8) `release`. `result.json` is `{"stage": "setup", "failed": "<step>"}` when a step before the tests failed (a fallback) or `{"stage": "tests", "exit": N, "report": "<text>"}` (a result for any N, including 5 "no tests ran"; the report is the text `forge test` printed in the box, with the box's log path replaced by the laptop's). A command status of `Failed`, `Cancelled` or `TimedOut`, or an instance that EC2 reports gone, with no `result.json`, is a fallback with the line `the box ended while the run was going`. The report says `exited with status {N} in a box` where a laptop run says `on this machine`. A hard kill of the laptop leaves the box to finish the command; the box's idle end and story 1's rules end it, and `tick` frees the place.
- **Box script** (`run_box.sh`, one run). Fetch and unpack the bundle into `/home/runner/runs/<id>`, check out the snapshot commit, set `refs/remotes/origin/<default>` from the bundle; read the test-files secret and write each listed file with mode 600, refusing a path with `..` or one outside the folder; run `FORGE_IN_BOX=1 forge test [--change]` with output to the log; upload `result.json`, the log and the results file; delete the folder, the files and the local bundle in a `trap` on exit. The repo's own test command starts any Docker service it needs.
- **Box start script** (`guest_tests.sh`, Ubuntu 24.04, root). Same order as story 1's `guest.sh`: record the start, arm `shutdown -P +180` first, then install `docker.io`, `docker-compose-v2`, `git`, `curl`, `jq`, `uv` and the AWS CLI version 2 (AWS's own installer; the builder pins its checksum), install Forge at the pin (`sync.install_line`), set the machine item's `ready`, mark every 300 s, and end with `poweroff` at the idle end (no run in `forge lanes --json` `tests.entries` for 600 s, counted from `ready`) or, after 7,200 s, as soon as the line is empty. `FORGE_IN_BOX=1` makes `machine.test_slots` use every processor, because a story 2 box runs no builders: with the laptop's half-for-agents rule a 4-processor box would run one 2-processor run at a time and never pack two. The marks, the 15-minute and 3-hour rules and the confirmed-termination rule are story 1's `reap.mjs` and `tick.mjs`, unchanged for `kind` `test`.
- **Snapshot** (`src/forge/box_ship.py`). A temporary index (`GIT_INDEX_FILE`), `git add -A` (git's own ignore rules apply), `git write-tree`, and, when the tree differs from `HEAD`'s, `git commit-tree -p HEAD`; a temporary ref names the commit while `git bundle create` runs, and is removed. The bundle holds that commit and `origin/<default>`. Nothing in the real index, the branch or the working tree changes.
- **Test files** (`aws.files`, in `aws.py`). `forge lanes --aws files` prints the candidates (ignored files from `git ls-files --others --ignored --exclude-standard`, less `repo.CACHES` paths, with sizes) and, for each name in `aws_test_files`, checks it (a real file inside the repo, not a symlink, ignored by git and not tracked, 64 KB for all together) and writes the whole set with `aws secretsmanager put-secret-value --secret-string file:///dev/stdin`. File text is never an argument, a log line or output. Run it again after a file changes.

Messages (new). Every refusal and fallback is one problem line plus a `Next:` line where there is a next step.

- Route: `This laptop is busy ({reason}), so this test run goes to an AWS box.`
- Fallback: `This test run goes back to the laptop line: {reason}.` with the reasons `AWS did not answer ({last line})`, `no box place is free (limit {n})`, `the box was not ready after 10 minutes`, `the box ended while the run was going`, `the box could not prepare the run ({step})`.
- Settings: `aws_tests is on, but aws_runners is not set, so this test run stays on this laptop.` / `Next: ask the owner to set aws_runners, then run forge lanes --aws setup`. Wrong account: story 1's line. No stack, or an old one: `The AWS stack for this repo has no test boxes yet, so this test run stays on this laptop.` / `Next: forge lanes --aws setup`.
- Files: `{path} is tracked by git, so it is code, not a test file.`, `{path} is not ignored by git.`, `{path} is outside this repo or a link.`, `The test files are {n} KB; the secret holds at most 64 KB.`, and `{path} is not in aws_test_files.` / `Next: ask the owner about {path}, then add it in a settings fix`.
