# Builder test runs go to a throwaway AWS box when the laptop is busy

6 parts · Risks: unsaved work and approved test files leave the laptop for your own AWS account; an existing AWS setup must be updated once; a box that ends mid-run loses that run's time · New moving parts: one private storage bucket, one second machine role, one test-files secret and one start script, all inside story 1's AWS stack; one setup option; two settings

## What changes for you

In this plan, a "box" is a throwaway AWS machine that runs your tests for you. A "test run" is the tests that a builder runs with `forge test` or `forge test --change`, and the test step of `forge close`. The "laptop line" is the queue that holds test runs on your laptop today.

- Box test runs are off by default. A new client repo gets them off at setup. An existing client repo has them off after it upgrades and syncs, and its settings and workflows do not change. Both get the new steps in Forge's guide. A repo that already runs story 1's AWS setup must run `forge lanes --aws setup` once more to add the box parts to its stack; until it does, a run says so in one line and stays on the laptop. (Source: your decision of 27 Nov 2026)
- Boxes work for public repos and private repos. To turn them on, the agent asks you, then a settings fix sets `aws_tests = true` in `forge.toml`. The repo also needs `aws_runners` (story 1's setting for the AWS account and region, written `"<account number>/<region>"`) and a stack. A new option, `forge lanes --aws setup --tests-only`, makes that stack with no GitHub App and no check of whether the repo is public; story 1's full setup also works. Story 1's rule, private repos and a GitHub App, stays for GitHub Actions runners only. Forge's own public repo can use boxes and tests them first. The same AWS account pays, and the same machine limit (1 to 4, default 2) covers Actions jobs and boxes together. (Source: your decision of 28 Nov 2026)
- With `aws_tests` on, a test run starts on the laptop while the load is under 0.75 per core (half of today's limit of 1.5) and the laptop is not swapping memory to disk. If either fails, the run goes to a box at once and prints one line that says which. With `aws_tests` off, nothing changes: no AWS call, and the run waits in the laptop line as today. A reading Forge cannot take, and every Windows laptop, keeps the run on the laptop. A run that is already inside a box never starts another box. "Swapping" means that the count of memory pages written to disk grew during one second (Linux `/proc/vmstat` `pswpout`; macOS `vm_stat` `Swapouts`). It does not mean "a swap file exists": on the laptop where this plan was written, 16,276 MB of 17,408 MB of swap is used at this moment, so that reading would send nearly every run to a box. (Source: your decisions of 27 and 28 Nov 2026)
- Only these runs can go to a box: `forge test`, `forge test --change` and the test step of `forge close`. The full suite, the retest before a merge, the replay of an older revision and the pytest picker stay on the laptop. (Source: the planner's choice; confirm)
- What goes to the box: one git bundle of the folder as it is now: your commits, your unsaved changes and your new files, but never a file that git ignores. The bundle goes through a private bucket in your AWS account, and the bucket deletes its files after 1 day. (Source: your decision of 28 Nov 2026)
- Ignored test files (for example a local settings file) can go too, one file at a time. The agent lists the ignored files a run may need, you say yes or no to each name, and each yes is a settings fix that adds the name to `aws_test_files` in `forge.toml`. `forge lanes --aws files` then copies exactly those files into one AWS Secrets Manager secret (at most 64 KB in all). Each box run reads the secret, writes the files into the run's own folder, and deletes them when the run ends. (Source: your decision of 27 Nov 2026)
- A box has 4 processors, 16 GiB of memory and Docker, and is the same kind of machine as story 1's. Forge runs inside it, at the version `forge.toml` pins. A box runs only tests, so its test line may use all 4 processors, and it holds at most two runs at once; its own test line decides when each starts, by its processors and memory, with the laptop's other lane rules. A box takes new runs only in its first 2 hours and ends by 3 hours (story 1's marks and 3-hour limit), and it also ends when it has run nothing for 10 minutes. A box that was just started is ready after about 2 to 5 minutes plus the install time. (Source: your decisions of 27 and 28 Nov 2026)
- When no box place is free (the limit is reached, or all boxes hold two runs), the run does not wait in AWS. It goes to the laptop line and says so in one line. (Source: the planner's choice; confirm)
- A box run gives the same result as a laptop run: the exit code, the names of failed tests, the one retry of failed files and the log. A failing test is a result. It never sends the run back to the laptop. When AWS or the box fails before the tests ran (a call fails, the box is not ready in 10 minutes, or the box ends while the run goes), the run goes to the laptop line with one line of reason, and only that run's time is lost. (Source: your decision of 27 Nov 2026)
- A box run shows in `forge lanes` and in the Forge pane as an ordinary test row marked "in a box", with its minutes. It takes no place in the laptop's test line. `forge stop <item>` ends it: the command is cancelled in the box and its place is freed. (Source: your decision of 27 Nov 2026)
- `forge lanes --aws off` (story 1) also deletes the bucket and the test-files secret, and checks that nothing is left. `forge lanes --aws status` also counts test runs and box minutes for the last 7 days, per branch. (Source: your decision of 27 Nov 2026; the `status` lines are the planner's choice)
- Estimates, not measured. A box costs about $0.198 an hour (story 1's number). A 10-minute test run in a box that is already ready costs about $0.03. A new box adds 2 to 5 minutes of start time. The test-files secret costs about $0.40 a month; the bucket costs cents. With the limit at 2, the worst case for 3 hours is the same as story 1's: about $1.19. Boxes add no new worst case, because they share its limit.
- Not known until the first real run: how long a box takes to become ready, how long the Forge install takes, if a fresh box has what a repo's own test command needs (language tools and packages), how big a bundle gets for a large repo, and how often the laptop is busy.
- The success measure is story 1's: the median time from the start of an item to its ready pull request over one week before and one week after, with the AWS cost per item and the load-caused test failures beside it. (Source: your decision of 27 Nov 2026)

Design: none (no new screen or page. The pane gets one label, "in a box", on rows it already shows. Setup, status and turn-off print lines in the agent's terminal.)

## Why

The laptop is the busiest part of the factory. Over 86 items from 11 to 14 Oct 2026, local tests and the wait for the test line took about 22% of item time, and a heavy laptop also makes tests fail for load, not for a bug. Story 1 builds the AWS side: one place where AWS decides how many machines may run, and one lifetime rule. This story uses it for the next simplest work: the test runs that already wait on the laptop. It keeps the laptop first, so a quiet laptop costs nothing. How much faster work gets ready is not measured yet.

## Done when

1. **With `aws_tests` unset, which is the default in a new repo and in an existing repo after upgrade and sync, a test run makes no AWS call and waits in the laptop line as before; with `aws_tests` set, a run stays on the laptop while the load per core is under 0.75 and the laptop is not swapping, and goes to a box at once, with one line that says why, when either fails; a reading Forge cannot take keeps the run on the laptop, and a run inside a box never starts another box.**
2. **A box run tests a bundle of the committed code plus a snapshot of unsaved files that git does not ignore, sent through the repo's private bucket; only the names in `aws_test_files` come from Secrets Manager, and `forge lanes --aws files` refuses any other path; and the run's folder, those files and the bundle on the box are deleted when the run ends, whether the tests passed, failed or were stopped.**
3. **`forge lanes --aws setup --tests-only` makes the stack with no GitHub App and no public-repo check, and a webhook with no App secret starts nothing; with the limit at 2, five test runs at once start at most two boxes with two runs each, the fifth is told no place is free, and a box counts against the same limit as an Actions job; a run joins a box only in its first 2 hours; a box is ready only when Docker, the pinned Forge and the AWS CLI work; a box ends by 3 hours, and after 10 minutes with no run; and the box role cannot read the GitHub App secret, nor can the Actions machine role read the test-files secret.**
4. **A run in a box returns the exit code, the names of failed tests, the one retry of failed files with its "Flaky test files" line, and the log, in the form a laptop run gives; a failing test is returned as a result and never sends the run back to the laptop.**
5. **When a call fails, no place is free, the box is not ready in 10 minutes, or the box ends while the run goes, the run goes to the laptop line with one line of reason, runs there once, and leaves no place held in AWS.**
6. **A box run shows in `forge lanes` (text and JSON) and in the pane as a test row marked "in a box" with minutes and takes no laptop test place; `forge stop <item>` cancels it and frees its place; `forge lanes --aws off` leaves no bucket and no test-files secret, and `status` counts test runs.**

## Risks

These steps are sensitive or cannot be undone:

- Your unsaved work leaves the laptop. It goes to a private bucket in your own AWS account, not to anyone else, and it is deleted after 1 day. A file that git does not ignore goes in even if it holds a secret, so keep secrets in ignored files. In a public repo, this is still your own account; nothing goes to the public repo.
- The approved test files may hold credentials. They sit in Secrets Manager and are read by the box that runs your tests, and the repo's test code runs there with internet access. Approve only values made for tests, never production keys. The box has its own role: it cannot read story 1's GitHub App key, and Actions machines cannot read the test files.
- An existing AWS setup is changed once, when the person runs `forge lanes --aws setup` again: a second machine role, a bucket and a secret are added to the stack. Nothing runs until `aws_tests` is set.
- A tests-only setup leaves story 1's web address for GitHub events in place with no App key behind it. It answers every call with a refusal and starts nothing. It cannot start a box for a stranger, because boxes start only from a call that your signed-in AWS account makes.
- A box that ends while a run goes (no marks for 15 minutes, 3 hours, or the idle end) loses that run's time. The run starts again on the laptop.
- A fresh box may lack what a repo's own test command needs. Then the test fails in the box for that reason and looks like a real failure. The first real runs measure this.
- Boxes can raise spend, up to story 1's worst case. The budget is still an email, not a stop.
- A wrong swap or load reading costs money (an extra box) or time (a slow laptop), never a wrong test result.
