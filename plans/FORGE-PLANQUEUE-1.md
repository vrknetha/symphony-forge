# Move story plans to approval without reminders

1 part · Risks: none one-way; four accepted limits · New moving parts: one lock file for each story being planned, and one hidden entry that the runner starts (not a command)

## What changes for you

- After you start a story, Forge writes its plan, has it read cold by the other tool, and answers the read notes. It does this in the background with no chat open. You send no message to move the plan from the first draft to the point where it can be approved. (Source: the owner's request, 27 Nov 2026)
- The same runner that moves approved work to merge (the story FORGE-RUNNER-1) does this. It starts the plan work by itself when you use Forge. There is no new helper, no new command and no new setting. (Source: the owner's request, 27 Nov 2026)
- It works the same when the repo's builder is Antigravity (Neon): Antigravity writes the plan and answers the read notes, and the cold read is done by the other tool, as today. (Source: the owner's choice, 27 Nov 2026)
- You are needed at two points only. First, to approve a plan: when it is ready you get one desktop notice, and you approve it as before (Plan Mode in Claude, the typed line in Codex). Forge never approves a plan. Second, when a cold read reaches its round limit with open notes: you choose one more round, split the plan, or accept it. (Source: the owner's request, 27 Nov 2026)
- When the plan writer has a question that only you can answer, or the story needs a screen design that a person must make, only that story stops. You get one notice with the question. The other stories and builds go on. (Source: the owner's request, 27 Nov 2026)
- Your coordinator no longer asks you one question at a time while the plan is written. Forge lists the choices it made alone when it answered read notes in the plan's Notes, and your coordinator shows that list to you once, when it asks for your approval. (Source: the owner's choice, 27 Nov 2026)
- Your coordinator agent no longer writes the plan, starts each cold read or answers each read note. It shows you the plan when a notice says it is ready, and it asks you the question when a notice says a plan needs you.
- What each repo gets: a new repo and an existing repo both get all of this on upgrade to the release that has this story, and `forge sync` refreshes the guide text. Nothing converts, and no setting changes. The story builds only after FORGE-RUNNER-1 has merged, because it extends that runner.

Design: none (no screen is added; the flow is: you start a story, Forge writes, reads and corrects the plan in the background, and a desktop notice reaches you when the plan is ready or needs you)

## Why

After the queue runner ships, building moves to merge without reminders, but planning still depends on an open coordinator chat. The chat must write the plan, start each cold read and answer each note. If nobody pushes it, a started story waits, no part becomes ready to build, and build places stay empty. The owner asked that nobody should have to push the agent to keep work moving. Forge already knows each story's state from its files: `forge next` says whether the plan needs writing, a read, answers to notes, an owner choice or an approval.

## Done when

1. **After you start a story, Forge writes its plan, has it read cold and answers the notes by itself, with no chat open, until the plan is ready or needs you. A restart repeats no finished step, and a plan that a person is editing is left alone.**
2. **When a plan is ready, you get one desktop notice, and nothing is built until you approve the plan yourself; Forge never approves a plan.**
3. **When a plan needs you (a read reaches its round limit with open notes, or the writer has a question only you can answer), only that story stops, you get one notice with the question and your choices, and your answer lets it go on.**

## Risks

Risks: none one-way. The part reverts with its pull request, and every plan change is a commit on the story's own branch.

Accepted limits:
- A story that adds a screen or changes a flow needs a design that a person makes in a chat. The writer sees this, asks its one question, and the story stops with a notice. The runner never makes a design.
- The runner plans only stories that have a folder on this computer, which is where `forge start` put them.
- A plan folder with changes that nobody committed is left alone, because a person may be editing it. The runner does not say so; `forge next` shows the same plan step as before. It looks again the next time you use Forge.
- The runner picks the reader the same way `forge read` does, so the other tool reads when both are installed. A repo that uses one tool (`tools` set to `claude` or `codex`) is read by that same tool. When `forge.toml` names a reviewer, or an earlier round was read by an installed tool, that tool keeps reading, even when it also wrote the plan. This is how `forge read` works in a chat today.

### Done-when details

1. New module `src/forge/planrun.py` (hidden entry, like the runner's: the runner starts it with `sys.executable -c` and `forge.planrun.main`, the same way `runner._child_cmd` starts `forge`; it is not a `forge` command, because Forge is at its limit of 26). It takes one story key, does exactly one step, and exits. Then the runner does another pass.
   - **Which stories.** In the runner's pass, after `startable` and the land starts, for each story that has a folder in `story.worktrees(top)` (branch `story/<KEY>`), that is not `done` or `dropped`, and for which `approval.waiting_digest(key, folder)` is not None. That is the same call `forge next` uses to say a plan waits for a first or a renewed approval, so a story whose approved text was changed (for example, when `forge start` adds an idea to it) is planned again, and an approved story that is unchanged is not. Every worker family is planned, Antigravity included.
   - **Which step.** The one source of truth is what `forge next` already prints for the story: read the `Next:` line of that story from `nextstep._report(top)`, the same report that `nextstep.startable` parses. `Next: forge read <KEY>` is the read step. `Next: give finding <N> in plans/<KEY>.read.md a disposition, then forge read <KEY>` is the answer step. The read-loop line is the owner stop (item 3). The "is waiting for approval" line is the ready notice (item 2). A story whose `plans/<KEY>.md` is still a draft has the write step, whatever `forge next` says. A plan is a draft while it still holds template text from `src/forge/templates/story.md`: any `<!--` comment, or the line `<Evidence, edge cases and the tests that prove item 1.>`. A Tasks row is not the test: a story promoted from a fix (`story.new` with `--from-fix`) starts with one row but is still a draft, and a draft where the writer stopped with a question after adding a row stays a draft until the writer finishes it. A fresh draft has an empty Tasks table and `forge next` says `forge read <KEY>` for it, which is why the draft test comes first. No new record is written: the next step comes from files in git each time.
   - **Write step.** One turn of the worker family (`repo.worker_family(cfg, design=False)`) with the design-kind model that the `planner` role uses (`repo.design_models`, see `roles.ROLES["planner"]`), in the story's folder, with write access, in one agent place (`machine.agent_slot`, kind `work`) and with `codex.hold` as `forge read` does. On Claude it runs through `worker._run`, which `forge work` uses. On Codex it runs through `codex.run` with a write sandbox. On Antigravity it runs through `worker._agy_turn`, the headless runner that `forge work` already uses for Antigravity builds (it calls `antigravity.turn` with `mode="full"`, the model from `antigravity.ready(cfg, "design", True)`, and the story key as the item). A question from Antigravity comes back as a trailing `Question:` paragraph, the same line the other two end with. Reuse these calls; write no new driver. The prompt is a new template, `src/forge/templates/plan-run.md` (two sections split by a marker, as `cold-read.md` is split: write, and answer). The write prompt tells the writer to fill each placeholder in the draft by its own comments (the parts count line, Risks, Done-when details, the Tasks table with Scope and Tests, the moving-parts line, Notes), to split into the fewest tasks that each prove Done-when items end to end by the rule the cold read applies (a task covers at most three Done-when items and about 400 changed lines; tasks have separate Scopes, or an After link), to remove every template comment and placeholder line, and to end with the `Question:` paragraph, as a builder does, when it needs the owner. Above `## Risks`, the owner's words from `forge start` (What changes for you, Why, Done when) keep their meaning; the writer may fix their wording only to make them plain and complete, may fill the parts count line, and must add the closing `Design: none (<why>)` line to What changes for you when the plan has a user-facing task that adds no screen and changes no flow (`design.check` refuses without it). A story that adds a screen or changes a flow stops with the design question (Accepted limits). When the writer asks a question, the prompt has it also write the question under "Question for the owner" in Notes, so the next write turn finds the owner's answer there. The step ends with `repo.commit_state` of the plan file, also when it ends with a question. A run that ends with a `Question:` paragraph, or when the story needs a design, exits non-zero with the line "needs you" and the question, which the runner sends to `stops.ended`, as it does for a land run.
   - **Read step.** The child runs `forge read <KEY>` as a subprocess with `FORGE_RUNNER=1` and the new `FORGE_RUNNER_AS=<the worker family>`. `repo.coordinator()` (`src/forge/repo.py`, 2 lines, the only change there) returns `FORGE_RUNNER_AS` when `FORGE_RUNNER=1`; `story._read` then picks the reader through `roles.read_family` exactly as for a chat, so with both tools installed the other tool reads (for an Antigravity writer, `read_family` offers Codex, then Claude). `story.py` is at 1,200 lines and does not change. `repo.py` is at 1,185 lines plus RUNNER's 3: keep the change to 2 lines and check the file stays at or under 1,200. A read round with findings leaves its notes file and the story's record uncommitted (`story._read` commits only a passing round, and not a stop at the round limit). So after `forge read` exits, the child itself commits `plans/<KEY>.read.md` and the story's record with `repo.commit_state`, whatever the exit code (a round-limit stop exits non-zero with the notes written). The next child then sees a clean folder, and the dirty-folder rule below never confuses the read's output with a person's edit.
   - **Answer step.** One turn like the write step, with the answer prompt: for every blocking note of the latest round, amend the plan when the note needs a change, and always write `Disposition: cut|defer|keep <reason>` directly under the note in `plans/<KEY>.read.md`, because the read gate (`story.undisposed`) refuses the next round for a blocking note with no disposition, even when the plan was amended (`keep` needs a reason, `cut` says what changed); change `What changes for you` or `Done when` only when a note requires it; and add every choice that picked a behaviour, a limit, a refusal or a scope cut to a list "Choices made while answering notes" in the plan's `## Notes`. Commit the plan and the notes. Then the next pass runs the next read round.
   - **Locks and restart.** Each child takes `repo.forge_dir(top)/plan-<KEY>.lock` with `codex._try_lock` and exits quietly if another child holds it (the same rule as the land lock). The plan step is chosen from the plan, the notes and the story's record only. When `git status` shows an uncommitted change to `plans/<KEY>.md`, `plans/<KEY>.read.md` or the story's record, the folder is a person's work in progress: the child changes nothing and exits with code 3 ("left alone"). The lock file's own content holds a marker: it is written when a write or answer turn starts and cleared after its commit. A child that finds the marker with a free lock knows a turn was killed. It does not restore anything and does not treat the folder as left alone: it runs the same step again on the files as they are, and the prompt tells the writer to finish what is there. Nothing is thrown away, so an edit that a person made after the kill is kept and is part of what the writer sees; it is committed with the finished step.
   - **Runner side.** Add to `runner.py` the plan children next to the land children: the same run table, log (`.git/forge/runner.log`), quiet set, retries (twice, then `stops.ended`), and a wake after each finished step. Exit 0 means a step is done and the pass runs again at once; it is not a merge check. Exit 3 ("left alone") adds the story to the quiet set, which the next wake (any forge command) clears, so an uncommitted edit does not start child after child. Exit with "needs you" goes to `stops.ended` and the quiet set, as for a land run. A plan step adds nothing to `worked_repos`, so a repo where the runner only planned gets no summary notice. A runner whose passes find no story to plan, no land to start and nothing waiting ends as `runner.py` already does.
   - Tests (new `tests/test_runner_plans_a_story_to_approval.py`, run the forge command, reuse the repo, gh stub and agent stub of `tests/test_land.py` for the writer and answerer, and the reader stub of `tests/test_codex_reader.py`): a draft story made by `forge story new`, then the one waking command, as the runner tests do. With nothing else run, the plan gains its task row and loses its comments and placeholders (including the top of the template, and a `Design: none (<why>)` line for a small screen change), round 1 of the cold read has one blocking note and the read's notes and record are committed by the child, the answer step writes a disposition under that note and amends the plan, round 2 says `No findings.`, and the story's record has no approval. Also: the story's Notes carry the "Choices made while answering notes" list; `tools = "claude"` with no session plans and reads the same way; a plan promoted from a fix (`forge story new --from-fix`) has a task row but is still written by the write step; a story whose approved text changed (an idea added by `forge start`) is read again and the writer, reader and answerer stubs run for it; and a repo with `workers = "antigravity"` (the Antigravity stub of `tests/test_antigravity_build.py`, `install_agy`) is written and answered by the Antigravity stub while the reader stub is the other tool.
   - Restart and person edits, same file: a runner killed with SIGKILL during the write turn of the stub, then woken again by the next command: the stub's log shows the write run twice, the stub's second run sees the half-written plan and a line a person added after the kill, and the finished plan has one task row set and keeps that line. A story whose folder has an uncommitted edit to its plan: the stub is not run, no notice is sent, the runner does not start a child again over the next ticks; after the edit is committed and another forge command runs, the planning continues.
2. Test in the same file: when round 2 passes, the stub notifier on `PATH` is called exactly once, its title names the repo and the story and its body says the plan is ready; repeated wakes and a runner restart add no call; no `task start` call and no approval record appear over the next ticks, and the runner ends with no summary call. Then `forge hook approval` with the stub owner's reply approves the plan, and the runner starts the first part (the crossing test with RUNNER's flow). The runner's source never calls the approval code: the proof is that behaviour, not a text search.
3. New `tests/test_runner_stops_a_plan_at_its_limit.py`: two stories planned together. The reader stub keeps reporting a new blocking note, so the first story reaches `cold_read_rounds` with open notes; the second story's stub passes and is ready. The first story gets exactly one notice whose body is the question `story.read_question` prints (plain words, with accept, more and split), and its stub reader is not run again over repeated wakes and a runner restart (the stop is parked until the story's files change, as RUNNER's `told` signature does). The second story is not held back. Then `forge read <KEY> --resolve more --reason "<text>"` by hand, and the next wake runs round 3 (the stub now says `No findings.`) and the ready notice follows. A third story whose writer stub ends with a `Question:` paragraph stops alone with a notice holding that question, the stub reader is never run for it, and after the plan file is edited and committed by hand it goes on.

Each new test names its story slug and number as existing tests do, so the rule checks pass.
