# Approved work keeps moving to merge without reminders

2 parts · Risks: none one-way; six accepted limits · New moving parts: one background runner process per computer

## What changes for you

- After you approve a plan, Forge starts every part that nothing blocks, builds it, checks it and merges it. You send no more messages. A part that waits for another part starts as soon as that part has merged. A fix that you start with Forge goes the same way, from its start to its merge. (Source: the owner's choice, 26 Nov 2026)
- One helper, the runner, does this in the background. Forge starts it by itself when you use Forge, approve a plan or open a chat in a Forge repo. It ends when there is nothing left to do. It is not a system service. After a restart of the computer, it comes back the first time you use Forge. (Source: the owner's choice, 26 Nov 2026)
- When one item needs you, only that item stops, and the other ready work goes on. An item needs you when a builder asks a question, a review loop reaches its round limit, a run is stuck, a fix needs a size decision, a tool needs setup, or a pull request (the request to merge the change into the main code) must be merged by a person. You get one desktop notice with the question or the pull request link. When all the work is done, you get one summary notice. (Source: the owner's choice, 26 Nov 2026)
- A stop that you set stays after a restart. Forge builds that item again only when you tell your agent to continue it.
- Status stays on the board and in the next-step report. There is no new screen, no new command and no new setting.
- Your coordinator agent no longer starts each approved part, starts each fix build, watches the background runs, checks the next step after every merge, or copies the queue into the handoff note. It answers the notices and the builders' questions.
- What each repo gets: a new repo and an existing repo both get all of this on upgrade to the release that has this story, and `forge sync` refreshes the guide text. Nothing converts, and no setting changes.

Design: none (no screen is added; the flow is: you approve a plan, Forge starts, builds and merges every part by itself, and a desktop notice reaches you only when one item needs you)

## Why

Coordinators stop after a plan is approved, so the owner must keep saying "keep going" and asking for status. Each approved part and each new fix then waits until an agent starts it by hand. The owner may ask for ten things at once, and every one of them must keep moving until its pull request has merged and its folder is gone. Forge already knows the whole queue (git, the `.factory` records and GitHub), and `forge land` already builds, checks and merges one item. Nothing runs it without a chat.

## Done when

1. **After one approval, every part of the story that nothing blocks starts, builds and merges (or becomes ready for a person to merge) with no further message from the owner, and a part that waits for another part starts when that part has merged.**
2. **A fix started with Forge is built, checked and merged the same way, and the folder of every merged item that holds no local changes is removed.**
3. **An item that needs the owner stops alone, and the other ready work keeps going.**
4. **The owner gets one desktop notice when an item first needs them, with its question or pull request link, and one summary notice when the work is done.**
5. **A restart repeats no finished build and undoes no stop that the owner set, and the runner comes back the first time Forge is used.**
6. **When the work is done, the runner ends and makes no recurring GitHub calls.**

## Risks

Risks: none one-way. Each part reverts with its pull request.

Accepted limits:
- A repo that uses one tool (`tools` set to `claude` or `codex`) now builds with no chat open. If that tool's kit is not installed, Forge stops that item once, sends a notice that names the setup step, and does not switch to the other tool.
- A pull request that a person must merge is checked on GitHub once for each such pull request: every minute at first, then at growing delays up to 30 minutes, for at most 24 hours. After that the runner ends, and the next use of Forge starts it again. A repo with nothing to do makes no GitHub call.
- On Windows there is no pop-up. A stopped item still shows in the next-step report with its usual next step, and running that step shows the reason again.
- A repo that pins an older Forge release is skipped by the runner. It builds with no chat only after it upgrades.
- The runner never builds a part on top of an unmerged part. A part that waits for another part starts after that part has merged. A folder that holds local changes stays where it is.
- Forge does not form a combined test run for several ready changes from the runner. `forge land --all` still does that when someone runs it.


## For the builders

### Shared seam (RUNNER commits it first; STOPS waits through After)

RUNNER's first commit adds `src/forge/stops.py` with these names as stubs, and calls them from the places named below: `stopped(top, item) -> bool` (stub: False), `lift(top, item)`, `add(top, item)`, `ended(top, item, code, lines)` and `summary(top, merged)` (stubs: do nothing). `runner.py` calls `ended` and `summary`; `task.require_active` (the one shared check, see item 5) calls `stopped`; `land.py` calls `lift` when a person runs it. STOPS fills `stops.py` and calls `add` from `machine.stop`; it never edits `runner.py` or `land.py`. RUNNER owns every guide file, including the text for notices and for continuing a stopped item, and the settings exception in item 1 (`src/forge/worker.py` and `src/forge/templates/brief.md`); STOPS starts after RUNNER has merged, and edits only `src/forge/templates/brief.md` beside `stops.py` and `machine.py`. The crossing test is in RUNNER's `tests/test_runner_moves_approved_work_to_merge.py`: a land run that exits non-zero ends the pass with no crash, and over the next ticks the stub agent's log still shows one run (no restart loop). STOPS keeps that test.

### Done-when details

1. New module `src/forge/runner.py`. `nextstep.py`, `story.py` and `codex.py` are at 1,200 lines, so none of them changes; `repo.py` gets 3 lines at most; `task.py` gets 3 lines (one in `stack_base`, two in `require_active`).
   - **Wake.** In `cli._run`, after a command returns 0 (beside the `machine.remember` call), call `runner.wake(Path.cwd())` (a lazy import). It returns at once when `FORGE_NO_RUNNER`, `FORGE_WORKER`, `FORGE_RUNNER` or `CI` is set (a CI job must not start work in the repos of the account it shares), when the folder is not in a Forge repo, or for a `hook` command other than `hook approval` and `hook context` (the approval and the chat start). Otherwise it calls `machine.remember(top)` and reads `runner.json` in the folder of `machine._repos_file()`. If its `pid` is alive (`codex._alive`, which also checks the start time), it touches `runner.wake`. If not, it starts the runner detached (a new session on Linux and macOS, `DETACHED_PROCESS` on Windows) the way `land._child` starts its child: `sys.executable -c` with Forge's own source folder first on the path (a bare `python` may not exist or may not see Forge), and with `CLAUDECODE` and `CODEX_THREAD_ID` removed from its environment so no round is handed to a chat. The runner first takes `runner.lock` with `codex._try_lock` and exits at once if another runner holds it, so a second start does no harm, and then sets `FORGE_RUNNER=1` in its own environment. Test-only variables, like `FORGE_CHECKS_POLL`: `FORGE_NO_RUNNER=1` (set for every test in `tests/conftest.py`'s `isolated_environment`, after the variables it clears; it already clears `CI`) and `FORGE_RUNNER_TICK`, the seconds between checks (2 by default).
   - **A pass.** The runner works on each `machine.remembered()` repo in turn, and skips a repo whose pin is not this release (`repo._pin(sync.read(top / "forge.toml")) != __version__`, the test `doctor.tidy_finished` already makes), so an older release never builds with no chat. It reads local files first: `story.worktrees(top)` with `task.branch_item` for started items, and the story records for approved stories. When it finds no started item and no approved story with an unstarted part, it makes no network call. Otherwise it runs `git fetch -q origin`, then `doctor.tidy_finished(top)`, then starts each part in `nextstep.startable(top)` with the subprocess `forge task start <KEY>/<TASK>`, one at a time. `startable` is the list `forge next` shows, so After links, overlapping scope and the developer assignment already apply, and `task start` checks them again. **No stacking:** because the runner sets `FORGE_RUNNER`, `task.stack_base` returns `None` (one line), so a part that waits for another part is not in `startable` until that part has merged, and two parts with overlapping scope never run together. A refusal such as "already started" (a coordinator was faster) is not a stop. Then, for every started item that is not merged or dropped, the runner starts the subprocess `forge land <item>` with `FORGE_RUNNER=1` when all of these hold: its land lock is free (below); no live run of it (the same test as `land._queue`: `machine.entries()` and `board.active_runs` with a live `process`); no round out with a chat (`land._pending`); `stops.stopped` is false; and it is not quiet or waiting for a retry. A fix that `forge start` made is such an item. The runner puts no limit on the number of land runs: each one waits for its own agent or test place inside `land`, a check wait holds no place, and a coordinator who starts several lands today gets the same. Output goes to `.git/forge/runner.log`; the runner takes no place itself.
   - **Land lock.** The single-item path of `land()` opens `repo.forge_dir(top)/land-<item with "/" as "-">.lock` and takes it with `codex._try_lock`, and holds it until the process ends (the system lets go of it however the process ends). If another process holds it, `land` refuses with "Another land run is working on <item>." and changes nothing. This is the one rule that keeps a second land run off an item: a replacement runner after a kill, a hand-run `forge land`, and a queue child all meet it, and the runner treats that refusal as quiet, not as a failure. The runner also reads the lock before it starts a child, so it does not start one that would only refuse.
   - **When a land run ends.** Exit 0 and `land._merged(top, branch)`: merged; another pass starts at once. Exit 0 with the line "is ready; a human merges": the item waits for a person's merge (see Polling). Any other exit 0 (a chat owes a handback, a stacked part waits for its base): the item is quiet and is tried again only after another item merges or `runner.wake` is touched. A non-zero exit with the line "needs you", or with the lock refusal: the first goes to `stops.ended`, the second is quiet. A non-zero exit whose lines show a short network problem or a GitHub read that stayed down after its built-in retries (the same test as `land._queue`: a line with a `repo.NETWORK` text or `repo.REFUSALS["no_github"][0]`) is checked first and counts as a retryable failure, even though `land` also printed "needs you" for that refusal. Any other non-zero exit without "needs you" (a git lock collision, a crash) is retried the same way: twice, 10 s and then 30 s later (`FORGE_NETWORK_RETRY_WAIT`, as `land._queue` does); a third failure goes to `stops.ended`.
   - **Polling.** One `land._merged` call per waiting pull request, 60 s after the item was ready, doubling to 30 minutes, for 24 hours at most. A merge starts another pass, whose first step removes the folder.
   - **One-tool repos.** `repo.route` returns "kit" when `FORGE_RUNNER=1`, and does not refuse for a missing session. `worker.ready` then stops with its own words when the SDK or the CLI is missing. That text goes to `stops.ended` as the reason.
   - **Settings.** The runner never edits a settings file. A fix whose Done-when names `forge.toml` (`task.settings_allowed`) may be built with no chat, and its builder may edit `forge.toml` (the named settings only): `worker.SETTINGS` (the "Workers never edit `forge.toml`" text, used in `_brief` in two places) gets one more text for that case, chosen with `task.settings_allowed(item, top, state)`, and `src/forge/templates/brief.md` says in its settings lines that a worker edits `forge.toml` only when its item's Done-when names it. Every other item keeps the old rule. The guide text says to start a settings fix with `--done` naming `forge.toml`.
   - Tests (new, run the forge command, reuse the `land` fixture, the gh stub and the agent stub of `tests/test_land.py`; the rules below sit in the first file): a two-part story whose second part has After on the first, with `merge = "agent"`: after `forge hook approval`, nothing else is run, and both parts merge in order and both folders are gone. With `merge = "human"`: the first part becomes ready, the stub gh reports its merge later, and the second part then starts and finishes; the second part is never started on top of the first, also with `stack` on. Two parts with overlapping scope never run together. A repo with `tools = "claude"` and no session builds and merges a fix. A coordinator's own `forge task start` for the same part causes no stop. A stub `gh` that stays down past its built-in retries for one land run and then answers: the runner starts the land again, the item merges, and no notice is sent (a `FORGE_NETWORK_RETRY_WAIT` of 0 keeps the test fast). A command with `CI=true` starts no runner. A repo whose pin is another release is left alone. While a land run holds an item, a second `forge land <item>` by hand refuses and starts no second agent run, also after the runner was killed and started again.
2. A fix started with `forge fix start` (the step `forge start` ends in) is a started item, and the wake after that command is enough. `doctor.tidy_finished` never removes a folder with local changes, so the runner leaves it alone and says nothing about it. Tests: a fix reaches merge with no other command, and its folder is removed, also when it merges while the runner polls. A fix started with `--done` naming `forge.toml`, whose stub builder edits `forge.toml`, keeps the edit and merges with no chat; the brief the stub receives for it lacks "Workers never edit `forge.toml`" and a fix that does not name the file still gets that line.
3. STOPS. Test: two fixes, and one builder asks a question (a `Question:` paragraph in its handback). The other merges, and the first stays stopped and builds nothing more. A fix that needs a size decision stops the same way.
4. STOPS. A notice is one call to `osascript` (macOS, the text passed as arguments) or `notify-send` (Linux, when installed). A missing notifier is not an error. The title names the repo and the item; the body is the question, the first line of the refusal with its next step, or the pull request link. The summary names the number merged and each item that still waits for the owner. Tests put stub notifiers on `PATH`: exactly one call for the item with the question, none more after repeated wakes or a restart, one summary call at the end, none when a runner started and found nothing to do.
5. STOPS. One small file, `.git/forge/runner.json` (`repo.forge_dir(top)`, written with a temporary file and `os.replace`, as `handoff_hook` does), owned by `stops.py`. It holds `{"stopped": [item, ...], "told": {item: sig}}` and is the only new record. `machine.stop` calls `stops.add` before it ends the runs (for each run that has an item, and for the named item when nothing runs). **One check for every path.** `task.require_active` (it already refuses a dropped fix, and every path that builds, closes or merges an item passes it: `forge land <item>`, each close round and the merge inside it, `forge land --all` and its queue children, a train member's merge, `forge merge`, `forge work`, through `close._worktree`) also refuses a stopped item with "<item> was stopped; forge land <item> continues it". No path has its own check, and the runner's own `FORGE_RUNNER` plays no part in it. **Continuing.** Only the single-item `forge land <item>` run by a person lifts the stop: when `FORGE_RUNNER` and the queue's marker (`land.QUEUED`) are both unset, it takes the land lock and then calls `stops.lift` (removing the item from both lists) before `close._worktree`. `forge land --all`, a run naming several items, and every queue child never lift it. If a merge train would still test a stopped item, `_queue` skips it in its selection loop with the same `task.require_active` call. **Stopping the land process.** After `stops.add` and the end of the queue runs, `machine.stop` also ends the process of each live check wait of that item (`board.active_runs(root, item)` entries with a `process` that `codex._alive` does not report as gone, ended with `codex._stop(process, False)`; a process Forge cannot verify refuses with the existing "cannot verify" words). A check wait holds no queue place, and the land process is the one that waits, so its end frees the land lock. A land run between steps exits at its next `require_active`. The runner never starts a stopped item. A parked (`told`) item is tried again only when its `sig` changes (the branch head, the state file text and the open question in `codex.record(top, item)`), when its pull request has merged, or when a person runs `forge land` on it. Tests: `forge stop <item>` during a slow stub build, with the runner killed and revived by the next command: the item is not built again, and a hand-run `forge land <item>` lifts the stop. `forge stop <item>` during the stub's check wait: its land process is gone within a few seconds, its lock is free, no `pr merge` call follows, and a hand-run `forge land <item>` right after starts with no "Another land run" refusal. With one item stopped and another ready, `forge land --all` merges the other and neither merges nor builds the stopped one, and the stop is still on record afterwards; `forge merge <item>` on the stopped item refuses and changes nothing. The runner killed with SIGKILL after a finished build and before the close, and again after the merge and before the cleanup: one agent run in the stub's log, one `pr merge` call, the folder gone, and the item merged once. A killed runner's land runs finish by themselves, and the next runner leaves alone any item whose land lock is held.
6. RUNNER. Test: after the last item merges, the runner process is gone within a few ticks, and the stub gh call log does not grow over the next ticks. Also, `forge lanes` in a repo with nothing to do starts a runner that ends with no gh call.

Each new test names its story slug and number as existing tests do, so the rule checks pass.

### Guide text

RUNNER (all guide files) removes from `src/forge/templates/skill.md` the coordinator steps that the runner replaces: starting a part after approval, "run `forge land <item>` for each in the background", the run-and-watch advice for queued work, and "run `forge next` after each merge to start what was unblocked". The "Start this task" and "Land it" rows stay as the way to act by hand. It adds how to see that the runner works (the board and `forge next` show the items), says to start and land by hand only when a notice says the runner cannot, how to read a notice, and that `forge land <item>` continues a stopped item. In the settings flow it says to start a settings fix with `--done` naming `forge.toml`, and the line "Workers never edit settings" in `skill.md` gets the same exception. The flow's step 3 in `src/forge/templates/adapters/AGENTS.md` changes the same way. Run `forge sync` for `AGENTS.md` and the two generated skill copies. STOPS adds only, in `src/forge/templates/brief.md` next to the `Question:` rule, that a builder's question stops only its own item and reaches the owner as it is written, so it must make sense alone.

## Notes

- Source: Astra's design of 26 Nov 2026 (`~/Workdir/forge-handoff-files/astra-queue.log`). The plan keeps its shared eligibility (`nextstep.startable`), its `forge land` reuse, its "park only the affected item" rule and its restart and idle-polling tests. It drops what the owner's fixed choices of 26 Nov 2026 cut: registration with the operating system at login (Forge starts the runner instead), a new board state "Merged · cleanup needs you" (status stays on the board and in the next-step report), and runner-owned settings.

- Size estimate: about 260 production lines in RUNNER and about 130 in STOPS (about 390 together), plus 150 to 250 lines of tests.
- Not in this story: merge trains formed by the runner, a Windows pop-up, a setting to turn the runner off, recording a story's outcome after a person merged its last part (the next-step report already asks for it), and any change to approvals, exceptions, merge settings, deferred ideas or deployment.
