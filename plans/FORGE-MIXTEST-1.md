# Run related tests locally and full suites on GitHub

2 parts · Risks: none one-way; four accepted limits · New moving parts: none

## What changes for you

- A repo can set `test_place = "mixed"` in forge.toml. With it, close runs the change's related tests on your machine, as it does today with `local`. When the related tests are most of the suite, close does not run them here. It sends the change's tests to GitHub, where they run in parallel across the test groups, and close waits for GitHub's `tests` check. (Source: the owner's request, 27 Nov 2026)
- "Most of the suite" means more than a third of the test files, or a change to a shared test input such as `pyproject.toml` or a root `conftest.py`. A small change still starts no test group on GitHub. It starts two short check jobs that report in about a minute. (Source: the owner's request, 27 Nov 2026)
- In `mixed`, the full-suite run before a release runs on GitHub, not on your machine. The generated workflow keeps a full-suite job that you start by hand, and it runs across the repo's test groups. The release check and the tag-push guard use the result of that GitHub run. Ordinary pull requests still run no full suite, and there is no nightly run. (Source: the owner's choice, 27 Nov 2026)
- What each repo gets: a new repo and an existing repo get no change. `test_place` stays `ci` or `local` as today, and the default stays as today. A repo uses `mixed` only after its owner or agent writes it in forge.toml through a settings fix. No command is added, and saved records stay as they are. A repo that uses `mixed` also gets the by-hand full-suite job in its workflow.
- This repo moves to `mixed` after this story merges and its release is installed, in one settings fix: the coordinator sets `test_place = "mixed"` in forge.toml and runs `forge sync` to rewrite the workflow. The required checks stay `forge-pr-check` only, so the owner changes no branch protection. After that fix, the full run before a release is started on GitHub, as the next step line says. (Source: the owner's request, 27 Nov 2026)

Design: none (no screen changes)

## Why

Today a repo picks one place for change tests. `ci` makes every pull request run tests on GitHub. `local` keeps GitHub use low, which this repo chose on 26 Nov 2026 to avoid another ban for heavy Actions use. But when a change touches a widely used file, the related tests are almost the whole suite. On one laptop that takes about 2 to 2.5 hours. Across 6 GitHub machines it takes about 25 to 30 minutes. For example, a small edit to `src/forge/close.py` selects 955 of the 960 test files. The full run before a release has the same cost. This story lets a repo keep ordinary changes local and send only these wide changes, and the release full run, to GitHub.

## Done when

1. **With `test_place = "mixed"`, a change whose related tests are a small part of the suite runs them on this machine at close, and its pull request starts no GitHub test group.**
2. **A change whose related tests are most of the suite does not run its tests on this machine. Close sends them to GitHub, where the generated workflow runs them across its test groups, and close does not pass the change until GitHub's `tests` check is green.**
3. **A repo that does not choose `mixed` gets the same settings checks and the same generated workflow as today.**
4. **With `test_place = "mixed"`, the full-suite run before a release runs on GitHub: the generated workflow has a full-suite job that runs by hand across the test groups, and the release check and the tag-push guard use only that run's green result. Ordinary pull requests start no full suite.**

## Risks

Risks: none one-way. The part reverts with its pull request.

Accepted limits:
- A failed by-hand full run in a `mixed` repo does not hold merges, as it does in a `ci` repo. The release check and the tag-push guard still refuse a release until a green full run is on the latest commit.
- Forge decides "most of the suite" only for Forge's own pytest picker (`fast_test = "forge test --pytest {base}"`, or no `fast_test`) with a plain pytest command that can be split into groups. A repo whose `fast_test` is its own script, such as the starter's `scripts/test.mjs` that prints "Affected parts: all", never counts as wide. The same holds for a repo whose test command is not pytest, and for a repo with `groups = 1`, which is what new repos start with (GitHub could not split the run). For these repos `mixed` acts as `local`.
- The laptop and the GitHub job run the same selection code. Close measures the branch from the point where it left the default branch, so changes that only reached the default branch do not make a change look wide; the GitHub job sees the same changes. If the two ever still disagree, a change that close sent to GitHub can pass there with its tests skipped. A new commit on the branch makes close decide again. The GitHub job never decides "narrow" when it cannot compute the selection: it runs the groups.
- After the default branch moves, `forge merge` retests the incoming changes on this machine, as it does in `local` mode. A wide incoming change is not sent to GitHub by this story.

## Notes

- Two parts. MIXED is one part, not two: the workflow side needs `fasttest.wide` and the `mixed` flag, and close needs the same two, so a split would only wait for the first. It is about 60 lines of code plus the tests and the guide text. FULL is separate only because a part may prove three Done-when items; it shares no file with MIXED and waits for the `mixed` flag (After). It is about 10 lines. MIXED owns `prcheck.py` and the guide files, so the guide text for the GitHub full run is written there and is true once both parts merge; the repo moves to `mixed` only after both.
- Module sizes (ceiling 1,200 lines, `test_5_forge_stays_small`): `repo.py` has 1,185 and gets at most 4 lines; `close.py` has 1,165 and gets at most 12, with `checks.py` (876) as the overflow; `review.py` has 1,200 and is not touched. New logic goes in `fasttest.py` (899), `prcheck.py` (662) and `review-tests.py` (319). Run the cheap repo checks from AGENTS.md before the round ends.
- Review rule (a change to what a coordinator or worker can use updates the skill or brief): `templates/skill.md` gets the new value in the test-place text (near lines 378 and 1757): what `mixed` does, how a repo chooses it (a settings fix that sets `test_place = "mixed"` and runs `forge sync`), and that the required checks stay as they are. `templates/brief.md` gets one sentence beside the `test_place` paragraph (line 329). The worker's own test step stays the `local` one, because a worker always runs related tests on its machine. The two synced skill copies are regenerated by `forge sync`.
- Why the workflow decides again and no new signal exists: the generated `docs-check` job already runs `.forge/review-tests.py` on every pull request and passes outputs such as `docs-only` and `one-group` to the `tests` job. This story adds one output beside them. A label or a commit status would need a new write from close and a new trigger on the workflow.
- What the required check is: no new required check. In `mixed`, `checks` can stay `["forge-pr-check"]`. The `tests` check is reported on every pull request (green at once when narrow), so a repo may require it in branch protection without blocking narrow changes. Close waits for `tests` by name only for a wide change.
- Guesses to confirm with the owner. (1) "The selection is the whole suite" is read as "more than a third of the test files, or a changed shared test input", because a real wide change such as `close.py` selects 955 of 960 files, not all 960. The ratio is the one the worker's broad-selection message already uses and is easy to change. (2) Forge's own pytest picker is the only selection that counts. (3) The settings fix for this repo waits for the release that has this story, because the pinned Forge (`v1.2.50`) refuses `mixed` as an unknown value until then. (5) The by-hand full run has no schedule, because the owner asked for it by hand and for the release check; a nightly run on GitHub is the cost this story avoids. (4) Ordinary pull requests still start two short check jobs (`docs-check` and `tests`); only the test groups are saved.
- Same as `ci` today, left alone on purpose: a named proof test that no group ran is not caught when the run is grouped (`proof.check` only counts a missing result when there is one group); wide counts every tracked test file, including ones outside the suite roots, so a repo with many example tests elsewhere may keep a wide change on the laptop, which is today's `local` behaviour; and a stacked task that waits for its parent says "tested" before GitHub's check, but it writes no Ready, and close runs again and waits after the parent merges.
